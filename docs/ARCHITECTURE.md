# Architecture

How glasshouse works as of 2026-11-10. Search by name; line numbers drift.

## The shape of it
A Tauri 2 app. Each window is a React 18 UI (`src/`) that calls Rust commands (`src-tauri/src/`) through `invoke`. The Rust side does all file-system, git, archive, process and terminal work, and sends events back (`fs-changed`, `pty-data`, `pty-exit`, `op-progress`, `config-changed`), each to the window it's for. Every window is in one process, as a browser's are: a second launch hands its window to the running app (`app_windows.rs`, `handoff.rs`). There's no server and no database: state lives in React, plus small JSON config files and `localStorage`.

**Where to start reading:**
1. `src/App.tsx`, the shell;
2. `src/handlers/index.ts`, where commands go;
3. `src/api.ts`, the backend surface;
4. `src-tauri/src/lib.rs`, the command registry, then the `commands/` module you need.

**State.** There's no store or reducer.
- `App()` holds about 40 `useState` hooks. The settings (`TweakState`: the look from `look.ts`, zoom, the file-list toggles, which panels are shown…) persist in `localStorage["glasshouse.tweaks"]` and are the same in every window (`useSharedSetting`); Preferences… and the View menu change them. Pins, tags and remotes written by one window are read again by the others on `config-changed`. The tabs persist through `session.ts`.
- Each tab is a headless `<TabShell>` running `useTabState` and passing `{state, actions}` up into `tabHandles`.
- Module-level state: `cmdState`, the undo stacks, the tag store (`tags.ts`, read with `useTags()`), the `dialogs` API and the git cwd.
- Components also signal each other with window events (`glasshouse:*`) and attributes on `<html>`.

**Commands are identified by their display label.**
- Menus, the palette, context menus and `KEYMAP` bindings all send a label string to `handleMenuCommand`. A palette row sends what a click on its menu item sends; its "Go to" row sends the typed path, which `navHandler`'s fallback opens (`looksLikePath` in `paths.ts`) as Go to Path… and Open… do: `openTyped` (`handlers/helpers.ts`) opens a link in the browser, a folder in the tab, or a file's folder with the file selected. See `docs/decisions/2026-11-13-paths-and-search-design.md`.
- It builds a `HandlerCtx` (with App's state and setters as `ctx.app`) and runs `COMMAND_CHAIN`. The first handler to return true wins, and the router shows errors in a dialog.
- Dynamic menu items (recents, bookmarks, open-with apps) carry a `payload` and go to `handleMenuPayload` instead.
- Renaming a label breaks routing unless its case changes too. `pnpm check:wiring` (`scripts/audit-wiring.mjs`, run in CI) fails on labels that nothing handles, cases that never run, no-op cases and cases nothing sends.
- See `docs/decisions/2026-11-10-split-big-files-app-routing.md`.

**Listing and refresh.**
- `useTabState` calls `list_dir`, which returns each entry with its git label scanned for that folder only, then `git_status` for the toolbar's git line.
- It then calls `watch_dir`. The backend sends `fs-changed` for the folder (300 ms debounce) and the tab re-lists. A 30 s poll is the backup.
- Each `watch_dir` needs one `unwatch_dir`. The backend counts them per folder, so tabs on the same folder share one watch until the last one leaves.
- `refreshGate.ts` runs one listing at a time per tab. One for a watcher report or the poll starts no sooner than 500 ms after the last ended, and reports in between become one trailing listing. A navigation and an explicit refresh (F5, or after the app's own change) start at once.
- Only the tab shown re-lists on reports and the poll. A tab in the background notes that it missed one and re-lists when shown.
- The sidebar tree watches its open folders on show the same way, and a report re-lists just that folder (a `RefreshGate` per folder). A listing drops what the tree kept for child folders that are gone (`treeRefresh.ts`). A click on a row asks `path_kind` (one stat) first, and a row whose file or folder is gone goes away instead of opening.
- The git dirty count needs a scan of the whole repo. `git.rs` keeps each repo's last count with the HEAD commit and index stamp it was counted at. `git_status(path, max_age_ms)` reuses it when those match and the scan is recent enough: a navigation accepts one up to a poll old, and a refresh one since it began, which a listing at the repo's root just made.

**Accessibility.** What a screen reader is given, and where the focus is.
- **The file list** (`FilePane`) keeps the DOM focus on the pane's `<section>`, which is a `grid` in the row modes and a `listbox` in the card modes (Icons, Tiles, Grid), named "Files in <folder>" (plus ", pane 2" in split view). It names the focused row with `aria-activedescendant`, only while that row is in the page: the row modes render a window of rows, so the grid also gives `aria-rowcount` and each row its `aria-rowindex`. Row ids come from `useId` plus a counter that goes up with each folder, so two panes never share one and a new folder's first row is a new node. A row's roles and `aria-selected` are props of that row alone, so a selection change still re-renders two rows (`FilePane.a11y.dom.test.tsx` counts them at 10,000 rows).
- **Column headers** are `columnheader`s with `aria-sort`. They take the focus from the keys only: Up from the first row (a new press, not a held key), then Left/Right/Home/End, Enter or Space to sort, Down or Escape back to the rows.
- **Tabs:** each pane's bar holds a `tablist`. The tab is the label (`role="tab"`, roving `tabIndex`, Left/Right/Home/End), and its close control is a `<button>` beside it, because a tab's children aren't exposed. `data-tab-bar`, `data-tab-index`, `.label` and `.tab-btn` are what tab dragging and the e2e suite find; keep them.
- **Dialogs:** every panel spreads `useDialogPanel(name)` (`dialogs/dialogPanel.ts`): `role="dialog"` or `alertdialog`, `aria-modal`, a name, the focus moved into the panel as it opens, Tab kept inside the topmost panel, and the focus given back on close. The keys behind a dialog are still `modal.ts`'s (`useModal`). Toasts go into a `role="status"` region that is always in the page.
- **Keys on a focused control:** `findBinding` skips `unlessHandled` bindings (Enter, Space) when the event's target is a button, link, tab or column header (`CONTROL_SELECTOR` in `keymap.ts`), so pressing one doesn't also open the selection. A mouse press on a tab or a toolbar button leaves the focus where it was, so the arrow keys stay in the file list.
- **Where the focus starts:** the active file pane takes the focus when the window opens and after a split or its closing rebuilds the panes (`App.tsx`). Tab and F6 still move between the panes (sidebar, file lists, terminal), not between controls.
- **Checks:** `a11y.dom.test.tsx` and `FilePane.a11y.dom.test.tsx` (roles, names, key paths in happy-dom), and `pnpm site:capture a11y`, which reads the accessibility tree headless Chromium builds for the demo (computed roles and names, the active descendant, modal dialogs, where the focus goes) and runs in CI's site job. `pnpm site:capture a11y dump [keys…]` prints that tree. WebKitGTK's tree and real screen readers are hand checks (`docs/testing/`).

**Paths.** Paths are plain strings. `paths.ts` applies the platform's rules (`IS_WINDOWS` comes from the user agent): `\` is a separator, and comparisons are case-insensitive, only on Windows. A listing gives each row a path under the folder it was asked for (`list_dir` joins the names to it), so a folder reached through a symlink, a junction or a mapped drive stays under that path, and so does everything keyed by it (tabs, recents, pins, tags, the session). Two tabs can then show one folder under two paths, so a copy or move asks the backend where its folders really are (`real_path`) before deciding that an item is already there, would go into itself, or sits inside what Replace would trash (`Places` in `transfer.ts`). On Windows the path a tab holds is the plain form: `plainPath` turns a verbatim path (`\\?\C:\…`, `\\?\UNC\server\share\…`) into the one people type wherever a tab is given one (`navInit`, `navGoTo`, a typed path, a restored session), and leaves it alone where the plain spelling would name something else (a trailing dot, a device name, a volume GUID). See `docs/decisions/2026-11-23-windows-paths-forms.md`.

## Backend (`src-tauri/src/`)
| Path | What |
|---|---|
| `lib.rs` | `APP_ID` (tauri.conf.json's identifier), plugins (log, dialog, the updater, which only `update.rs` calls; window-state below), managed state, and every command in `generate_handler!`. A window process first offers its window to a running glasshouse (`handoff.rs`) and exits if it's taken. Otherwise the app is built, then run: in between it claims the session (`session.rs`) and, if it owns it, registers the window-state plugin, which restores each window's size and place by label as it's made and saves them on exit. When the app is ready, `app_windows.rs` opens the first windows (the saved ones, or the launch's), each fitted to its monitor's work area by `window_fit.rs`; at exit the session is written and its lock let go |
| `app_windows.rs` | Every window, in one process: labels `main` and `main-<n>` (the config's window has `"create": false`, so all are made here), what each page starts with (`window_start`: plain, a launch, a restored record, or the v1 key), each window's session report and focus, New Window (`new_window`), Quit (`quit_app`), the startup ID for a handed-off window (Linux), and dropping a window's folder watches and terminals when it closes or its page loads again. See `docs/decisions/2026-11-21-split-and-tear-off-one-process.md` |
| `tab_drag.rs`, `tab_drag/` | A tab dragged out of its window. The page hands over the tab's record as the drag leaves; it's held in memory with the source window and tab until the drag ends, and cleared on every ending. Each window sends its tab bars and file areas (`tab_drop_zones`); `zone_at` hit-tests them in CSS pixels and the window under the drag draws the mark (`tab-drag-over`). A drop on a window sends it `tab-drop`; a drop on nothing opens a new window with the tab (`Start::Transfer`), with the pointer over its tab and fitted to the work area (`torn_rect`). Linux: a GTK drag with one target, `application/x-glasshouse-tab`, that every window's webview answers (`gtk_dnd.rs`); other drags go on to WebKit. Windows: `GetCursorPos`, `WindowFromPoint` and `GetAncestor` find the window under the cursor (`win32.rs`). Also Move to New Window (`tab_to_new_window`) |
| `handoff.rs`, `handoff/` | A second launch hands its window to the running app: the name `io.github.johnson_anthony.glasshouse.App` on the session bus (`dbus.rs`, Linux) or a per-user named pipe (`pipe.rs`, Windows), `AppDebug` in a debug build. The launch waits 1.5 s at most; with no bus, no answer or any other failure it runs on its own and logs why. Requests wait in an inbox until the app is ready. See `docs/decisions/2026-11-21-split-and-tear-off-handoff.md` |
| `diagnostics.rs`, `fatal.rs` | The log (`glasshouse.log` in `<data_local>/<APP_ID>/logs`, through tauri-plugin-log, with each start's version, OS, desktop and web view), the panic hook, and `bug_report_info`/`log_dir`. A panic in a release build, or a failed start, shows a native box from a new process, `glasshouse --fatal-dialog <why>` (`fatal.rs`: GTK on Linux, MessageBoxW on Windows); without WebView2 the box links to its download. See `docs/decisions/2026-11-20-diagnostics-and-errors-design.md` |
| `error.rs` | `AppError { kind, path, message, detail }`, what the commands users hit return: a sentence ("Couldn't open “x” because you don't have permission.") built from the `io::ErrorKind` and an `Action`, with the raw error as `detail` |
| `migrate.rs` | First thing in every mode: moves the folders named after 0.2.0's identifier, `sh.glasshouse.viles` (config, data and cache; the webview's localStorage is in the data one), to `APP_ID`'s, and `~/.glasshouse/remotes.json` into the config folder, unless the new ones exist. See `docs/decisions/2026-11-20-release-identity-migration.md` |
| `window_fit.rs` | The window fits the screen: with nothing saved, the config's size capped at 90% of the work area, centered; a restored or second window that doesn't fit shrinks and moves inside. See `docs/decisions/2026-11-20-first-run-defaults.md` |
| `winpath.rs` | Windows path rules as pure functions over strings, compiled and tested on every platform: the plain and verbatim forms (`plain`, `listing_base`, `verbatim`), `to_verbatim` for the raw `MoveFileExW`, `CopyFileW` and `ReplaceFileW` calls (so they work past MAX_PATH), DOS device names, saved paths moved out of the verbatim form (`saved_paths`, `saved_tags`, which `commands/config.rs` runs when it reads pins, recents and tags), and telling WSL's `bash.exe` launcher from a shell. See `docs/decisions/2026-11-23-windows-paths-forms.md` |
| `startup.rs` | The command line: a window (with `--select`/`--properties` and paths or `file://` URIs), `--dbus SERVICE…` (the resident), `--integration-on`/`--integration-off`, `--fatal-dialog`. Also `self_exe` (the AppImage file itself for an AppImage) and the XDG activation token handoff to GTK. See `docs/decisions/2026-11-20-folder-handler-processes.md` |
| `resident.rs` | Linux: `glasshouse --dbus file-manager`, a windowless process that owns `org.freedesktop.FileManager1` and asks the running app for a window per call (`handoff::send`, with the caller's startup ID), or, with none running, starts a window process, passing the ID on as `DESKTOP_STARTUP_ID`. Every resident also serves `io.github.johnson_anthony.glasshouse.Resident1` (`Version`, `Release`; `APP_ID` with `_` for `-`), which is how the app tells it's ours and takes the name back (it also knows the interface from before the identifier changed). `--dbus file-chooser` is the second service (`portal.rs`); one process can serve both |
| `portal.rs`, `chooser.rs` | Linux: the xdg-desktop-portal FileChooser backend (`org.freedesktop.impl.portal.desktop.glasshouse`). `portal.rs` answers `OpenFile`, `SaveFile` and `SaveFiles`, exports each call's Request (its `Close` kills the dialog) and starts one `glasshouse --chooser` window process per call, the request as JSON on stdin and the answer as one JSON line back. `chooser.rs` is that process's side: the request for the page, the parent window (X11 transient-for, Wayland xdg-foreign), the first-paint time, and the answer. See `docs/decisions/2026-11-20-file-chooser-backend.md` |
| `session.rs` | The saved session, `session.json` in the app config dir: every window's last report, written half a second after a change and at exit, read and checked at start. The process that holds a lock on `session.lock` owns it: the first plain start. One started with paths is a guest that restores and saves nothing, until a plain launch handed to it can take the lock. See `docs/decisions/2026-11-21-split-and-tear-off-session.md` |
| `commands/` | The commands, one module per area: `listing` (rows keep the path asked for; the canonical one is worked out only to look up git status), `fs_ops`, `file_info`, `search`, `replace`, `archive`, `hash`, `git`, `config`, `system` (Windows drive letters, and which share each mapped drive stands for, in `drive_letters.rs`), `wsl` (one timed, cached `wsl.exe --list` for the sidebar and the terminal profiles), `launch` (Reveal on Windows selects the file through the shell, `win_reveal.rs`), `places` (the desktop's bookmarks for a first run's pins: GTK's bookmarks file, KDE's places, Quick Access on Windows), `open_with` (the apps for a file and starting one: `xdg_apps.rs` reads shared-mime-info, desktop entries and `mimeapps.list` on Linux; `win_open_with.rs` asks the shell on Windows), `drag_out` (a native drag of files into other apps: GTK on Linux, OLE through the `drag` crate on Windows; it holds the drag while the OS has it, so a drop on any glasshouse window is a move, see `docs/decisions/2026-11-22-cross-window-file-drag.md`), `clipboard` (Copy, Cut and Paste through the OS clipboard: `clipboard/formats.rs` builds and reads the formats as pure functions, `linux.rs` is GTK's clipboard with callbacks answered through a channel, `win32.rs` is `CF_HDROP` with `Preferred DropEffect`; it holds glasshouse's cut for as long as the clipboard does and sends `clipboard-cut` when that changes), `trash` (Move to Trash, and the Trash dialog's list, restore and purge; `recycle_bin.rs` checks a Windows drive has a Recycle Bin), `integration` (Preferences → Integration: `integration_xdg.rs` writes and undoes the Linux files, mimeapps.list included; `integration_portal.rs` does the open and save dialogs: the portal's version and config search, portals.conf edits, the .portal, service and environment.d files, the portal restart; `integration_win.rs` plans the Windows registry changes, which only its `reg` module makes; see `docs/INTEGRATION.md` and `docs/decisions/2026-11-20-file-chooser-integration.md`). Tests are inline or in `<module>_tests.rs`; shared helpers are in `testing.rs`, where `have_tool` makes a test that needs git, tar or 7-Zip fail on CI when the tool is missing instead of skipping |
| `update.rs` | Updates: how this copy was installed, the once-a-day gate (`update.json` in the config dir), the check, and the download and install through tauri-plugin-updater, with `update-progress` events. Failures are `AppError`s: a sentence, with the plugin's own text as the detail. See "Updates" below |
| `ops.rs` | `OpRegistry` and `Op`: `op-progress` events to the window that started the op (at most every 100 ms, with an optional `detail` line) and cancellation for calls given an `op_id`, plus `cancel_op` |
| `pty.rs`, `pty/profiles.rs` | Terminal sessions (portable-pty; per session a reader, a wait and a writer thread, with `pty_write` queuing onto the writer), each sending to the window that started it and killed with it; shell, WSL and ssh profile detection and `check_profile`. On Windows the shells are PowerShell, Command Prompt, then a `bash.exe` that is not the WSL launcher (Git for Windows, also looked for in its install folders) |
| `watcher.rs` | Folder watching (notify, 300 ms debounce), counted per window and folder with one OS watch per folder, emitting `fs-changed` to the windows watching it. `PathEvents` wraps the OS watcher and drops events that name no path (inotify gives one for a watch that was just removed), which notify-debouncer-full 0.4 panics on |
| `proc_tree.rs` | Spawns a process so its whole tree can be killed (Unix process group, Windows job object); used by `run_script`'s 60 s timeout, and by `git_run` through `spawn_detached`, which on Unix also leaves the app's session so nothing can prompt on its terminal |
| `build.rs`, `permissions/app.toml`, `capabilities/default.json` | The app ACL: every command belongs to a permission group, granted to the app's windows (`main`, `main-*`) and their local pages only. `build.rs` fails if a registered command isn't in `app.toml` |

**Conventions.**
- Commands return `Result<T, AppError>` (`error.rs`) where the user sees the error, else `Result<T, String>`; a few return `Option` or a default. `From<String>` lets a converted command call string-returning helpers with `?`.
- Commands that do I/O are `#[tauri::command(async)]` and run on Tauri's worker threads. Those that rely on call order stay on the main thread: config read and write, `watch_dir`/`unwatch_dir`, and `pty_write`/`pty_resize`/`pty_kill`. See `docs/decisions/2026-11-08-async-commands-threading.md`.
- **File writes never clobber.** Create, rename, copy and move refuse an existing target (`create_new`, `RENAME_NOREPLACE` or `MoveFileExW` without replace, `CopyFileW` with fail-if-exists). The frontend's Replace choice trashes the old item first.
- **Find & Replace changes only UTF-8 text, atomically.** `replace.rs` works on bytes and lists the files it won't touch (other encodings, binary, too large, read-only, hard-linked). It writes each file through a temp file in its folder and a rename (`ReplaceFileW` on Windows), keeping its permissions. It never writes through a link or outside the searched folder. Undo goes the same way (`rewrite_text`). See `docs/decisions/2026-11-12-find-replace-safety-design.md`.
- **Failures clean up, and readers never block.**
  - A copy that fails or is cancelled removes what it made. A cross-volume move whose delete fails removes a file's copy, or keeps a folder's complete copy and says so.
  - File readers (previews, hex dump, hash, diff and blame, zip compression, copy) open through `open_regular`, which refuses FIFOs, sockets and devices without blocking on them.
  - See `docs/decisions/2026-11-12-fs-robustness-failures.md`.
- **Launching never builds a shell command line from user strings.** Arguments are checked (`check_profile`, `check_git_args`, `open_url`'s scheme list), and Windows paths go through the opener, direct spawns or environment variables. See `docs/decisions/2026-11-08-command-security-design.md`.
  - A desktop entry's `Exec` is split into words before its field codes are expanded, so a file name is always whole arguments; a field code inside quotes is refused. On Windows, Open With starts the shell's own handler (`IAssocHandler::Invoke`). See `docs/decisions/2026-11-20-open-with-linux-apps.md` and `…-windows-handlers.md`.
  - Custom Command…'s line is split in `commandLine.ts` and started directly; `{}` is the file. See `docs/decisions/2026-11-20-open-with-custom-command.md`.
- Git uses libgit2 for status and numstat, and the `git` CLI for history and for running menu commands (`git_run`, limited to `GIT_RUN_ALLOWED`).
  - Stage, Unstage and Discard use libgit2. Discard never deletes: it restores tracked files from HEAD, moves untracked items to the trash, and leaves staged-only and ignored ones alone. Branch switches end with `--`. See `docs/decisions/2026-11-11-git-safety-design.md`.
  - `git_run` never waits on a prompt. git runs with stdin closed, `GIT_TERMINAL_PROMPT=0` and (on Unix) no controlling terminal, so a credential nothing can supply fails at once. Each run is an op: git's `--progress` lines go to the tray, Cancel kills its process tree, and pull, push and fetch stop after 120 s with no output. A commit needs `-m` or `--amend --no-edit`, so no editor opens. See `docs/decisions/2026-11-20-git-ux-remote-commands.md`.
- Platform splits: `cfg(windows)` covers Win32 drives, hidden attributes (the only thing that hides an item there: dotfiles show), long paths (`winpath::to_verbatim` around the raw file calls; `longPathAware` and `supportedOS` in `windows/app-manifest.xml`, which `build.rs` links into every exe), WSL, shortcuts, signatures, job objects and `CREATE_NO_WINDOW`. `cfg(not(windows))` covers sysinfo drives, desktop entries for Open With (`xdg-open` only as a fallback), FileManager1 reveal (answered in the window itself when glasshouse is the file manager), terminal discovery, XDG trash and the `/proc` parsers.
- Pins, tags, saved remotes and recents are JSON in the app config dir (`~/.config/<APP_ID>` on Linux, `%APPDATA%\<APP_ID>` on Windows), written atomically (a synced temp file, then a rename). A missing pins file reads as null, which tells a first run (`places.ts`) from pins the user removed. The webview keeps `localStorage` in the app's local data dir (`~/.local/share/<APP_ID>`; `%LOCALAPPDATA%\<APP_ID>\EBWebView`). Tags are keyed by path; the frontend moves and drops keys as the app changes files (`tags.ts`). On Windows, pins, recents and tag keys that an earlier build saved in the verbatim form (`\\?\…`) are moved to the plain one when the file is read, and written back once (`winpath.rs`).

## Build, CI and release
- **CI** (`.github/workflows/ci.yml`):
  - frontend: build, test, `check:wiring`;
  - backend on Ubuntu, Windows x64 and Windows arm64: clippy with `-D warnings`, cargo test;
  - `notices`: `pnpm notices --check` against the lockfiles.
  - `installers` (Windows): a debug build of the NSIS and MSI installers with their hooks (`src-tauri/windows/`), then `scripts/installers-check.ps1` installs each, turns "Open folders with glasshouse" on, uninstalls and checks the registry, the NSIS install-folder keys included.
- **e2e** (`.github/workflows/e2e.yml`): the end-to-end smoke test (below) on ubuntu-22.04 and windows-latest. It runs on pushes to main and by hand, and isn't a required check.
- **Releases:** `release.yml` runs on a `v*` tag. It builds the Windows installers (msi, NSIS; x64 and arm64) and Linux packages (AppImage, deb; x64 and arm64) with tauri-action into a draft, each signed for the updater, then adds `SHA256SUMS`, a build provenance attestation for it (`gh attestation verify`) and `latest.json`, and publishes. It needs the update signing secrets (see "Updates"). The Linux menu entry comes from `src-tauri/linux/glasshouse.desktop`. The bundle metadata, the publisher (which names the Windows registry key `HKCU\Software\Anthony Johnson\glasshouse`) and the pinned MSI upgrade code are in `tauri.conf.json`; see `docs/decisions/2026-11-20-release-identity-installers.md`.
- **Locally:** `pnpm tauri build --no-bundle` makes a release binary, `src-tauri/target/release/glasshouse`, without packaging it.
- **Third-party notices:** `pnpm notices` (`scripts/gen-notices.mjs`, cargo-about) regenerates `src/assets/third-party.json`.

## Updates
Off until the user asks: Help → Check for Updates checks once, and Preferences → Updates → "check for updates automatically" (`autoUpdate` in the settings, off by default) checks at most once a day. Nothing else touches the network. See `docs/decisions/2026-11-20-updater-design.md`.
- **The check** is one GET of the latest release's `latest.json` (`plugins.updater.endpoints` in tauri.conf.json), made in Rust by tauri-plugin-updater (`update.rs`). The webview has none of the plugin's permissions, and the CSP's `connect-src` stays local. The automatic check runs only in the process that owns the session, 20 s after start and then hourly; every window asks, and Rust takes one automatic check at a time, so the first one's answer makes the others not due; Rust lets it through a day after the last answer (an hour after a failed attempt) and reports each version once, kept in `update.json` in the config dir.
- **How a copy updates** follows how it was installed: `tauri::utils::platform::bundle_type()` reads a marker the bundler writes into each package's copy of the binary.
  - The NSIS setup and the MSI download and run the new installer of the same kind (latest.json's `windows-<arch>-nsis` and `-msi` entries), so a per-user install stays per user and a per-machine one per machine.
  - An AppImage (`$APPIMAGE`) is replaced in place and restarted, if its folder is writable.
  - A .deb or .rpm gets a link to the new package, and a build from source (no marker: `tauri dev`, `tauri build --no-bundle`) a link to the release.
- **Trust:** each package is signed with a minisign key (`tauri signer`). The app installs one only if its signature checks out against `plugins.updater.pubkey` and names the version latest.json announces (`requireSignedVersion`). The private key and its password are the repository secrets `TAURI_SIGNING_PRIVATE_KEY` and `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`; a new key would strand every installed copy.
- **The release workflow:**
  - prepare stops a run whose secrets are missing, or whose key doesn't match the public key: it signs a probe and checks it with `scripts/updater-json.mjs verify`;
  - the builds sign their packages through `--config src-tauri/release.conf.json`, which turns on `createUpdaterArtifacts`. CI's and local bundle builds don't, so they need no key;
  - publish checks every package against its `.sig` and writes `latest.json` (`scripts/updater-json.mjs write`), with the CHANGELOG section as the notes. tauri-action's own latest.json is off, because each of the four build jobs rewrites it and they race.
- **Trying it locally:** build with a throwaway key pair (`pnpm tauri signer generate`) and a `--config` overlay that sets its `pubkey`, a local `endpoints` URL and `dangerousInsecureTransportProtocol`, then serve a latest.json from a folder. Never commit the overlay or the key.

## End-to-end tests (`e2e/`)
These drive the real app, built with `pnpm tauri build --debug --no-bundle`, through W3C WebDriver.
- **Driver chain:** `e2e/webdriver.mjs` (a small client over `fetch`, with a deadline on every request) → `tauri-driver` 2.1.0 → WebKitWebDriver on Linux or msedgedriver on Windows → the app. tauri-driver sets `TAURI_WEBVIEW_AUTOMATION=true`, which Tauri reads to allow automation, so the app has no test code. There's no macOS driver.
- **Harness** (`e2e/harness.mjs`): finds the binaries (overrides: `E2E_APP`, `E2E_TAURI_DRIVER`, `E2E_NATIVE_DRIVER`), makes the scratch folder and the fixture, starts tauri-driver and stops its whole process tree, and takes the desktop screenshot.
  - On Linux, the app gets a minimal environment: a scratch HOME and XDG dirs with the known folders and `user-dirs.dirs`, `GDK_BACKEND=x11` and no `WAYLAND_DISPLAY`. It also runs on a private session bus whose config starts no system services (`sessionBus`), so a local run touches none of the user's session.
  - On Windows, it runs as the runner's user, because known folders come from the profile. tauri-driver starts through `e2e/unelevated.ps1`, without admin rights: an elevated WebView2 ignores the `WEBVIEW2_*` variables msedgedriver attaches through, and GitHub's runners run steps elevated (`docs/decisions/2026-11-20-e2e-windows-elevation.md`). The WebView2 profile is msedgedriver's scratch folder; the app's config folder is the runner's own.
- **Flow 1** (`e2e/smoke.test.mjs`):
  - the window renders with no notice, pane error, dialog or crash screen;
  - the log has this run's start line and no error after it;
  - Ctrl+L, a typed fixture path and Enter list the fixture's entries;
  - the sidebar's DEVICES lists `/` or `C:\`, and the tree shows home with Documents and Downloads;
  - there are no uncaught errors or unhandled rejections from the session's start. On Windows, msedgedriver's browser log (`ms:loggingPrefs`) also covers the time before that, and any Content Security Policy violation fails the test too.
- **Flow 2** (split view): Ctrl+\\ splits, a tab dragged by WebDriver pointer actions moves to the other pane, Ctrl+F6 moves the focus. **Flow 3** (new window): Ctrl+N opens a second window (`main-2`) in the same process, which lists home in one tab; a theme set in it reaches the first window, which keeps its tabs; closing it leaves the first. **Flow 4** (move to new window): a tab with a Back history, moved by its menu's Move to New Window, opens in a second window with that history (Alt+Left goes back), and leaves the first window, whose other tabs stay. **Flow 5** (the OS clipboard): another app is on the other side, xclip on Linux and `e2e/windows-clipboard.ps1` on Windows (`osClipboard` in the harness). It reads what Copy, Copy Path and Cut offered (on Linux every target, byte for byte); its own copy ends a cut (the row un-dims); a cut pasted in a second window moves the file and empties the clipboard; its copied and cut files paste in glasshouse as a copy and a move. **Flow 6** (a folder reached through a link, Linux): Go to Path on a symlink to a folder; the rows, a folder opened from it, the watcher, git status, a tag, a pin, rename, cut and paste, the trash, their Undo and Redo, and the saved session, recents, pins and tags all go by the path through the link; a cut pasted into the same folder by its real path is "already there". The debug build's handoff name is `AppDebug`, and the private bus keeps it from any glasshouse the user runs.
- **Artifacts:** `e2e/artifacts/` (ignored by git) gets them on every run:
  - a webview screenshot after each test, and `desktop.png`, taken while the app is open;
  - `driver-and-app.log` (both drivers' output and, on Linux, the app's stderr; on Windows it's usually empty);
  - `session.json` (the drivers and the versions they report), and the page's text and errors;
  - `glasshouse.log`, the app's log from this run's start line on;
  - on Windows, `session.txt`: `query user`, the screens, the app's process session and window rect (`e2e/windows-desktop.ps1`).
- **Running it:**
  - Linux: `pnpm e2e` (Xvfb at 1920x1080x24 through `xvfb-run`). It needs `webkit2gtk-driver` and `xclip` (apt) and `cargo install tauri-driver --version 2.1.0 --locked`. Run it in a memory-capped scope; the app and WebKit take about 300 MB.
  - Windows: `node --test e2e/smoke.test.mjs` in an interactive session. First run `e2e/edgedriver.ps1`: msedgedriver must match the WebView2 Runtime in the first three version parts, or the session start hangs. The script uses the runner image's driver when it matches and otherwise downloads the matching one, then sets `E2E_NATIVE_DRIVER`. An elevated terminal is fine, because the harness drops admin rights for tauri-driver and the app.
- **Adding a flow:** poll with `waitFor`, never sleep, because listings and watcher refreshes are asynchronous. Read the page with `session.execute`, and type with `sendKeys` or `chord`, so the input goes through real key events. See `docs/decisions/2026-11-20-e2e-smoke-design.md`.

## Project site (`docs/` on GitHub Pages)
- `docs/index.html` with `docs/assets/site.css` and `site.js` is the landing page, hand-written with no build step. It uses the app's theme tokens (`docs/assets/themes.css`: the site build copies `src/styles/themes.css` up to its "site cut" line, the eight themes the page offers).
- `site/demo/` is a browser demo of the real UI. `main.tsx` installs `@tauri-apps/api/mocks` before importing `App`, and `mock/` holds an in-memory file system, a pretend git repo and shell, and one handler per command. It starts in the look from before themes-and-cosmetics, which the site's images show; `?theme=<id>` and `?look=<preset>` start it in another. `pnpm site:build` (`vite.site.config.ts`) builds it into `docs/demo/`, which is committed.

- After UI changes: `pnpm site:build`, `pnpm site:capture`, `pnpm site:capture check`.
