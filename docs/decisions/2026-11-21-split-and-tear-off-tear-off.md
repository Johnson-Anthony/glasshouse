# split-and-tear-off: tearing a tab off, in one process

Date: 2026-11-21. Task: `split-and-tear-off` (survey-3 task 50, phase 3). Plan: `docs/plans/completed/split-and-tear-off.md`. Code: `src-tauri/src/tab_drag.rs`, `tab_drag/gtk_dnd.rs` (Linux), `tab_drag/win32.rs` (Windows), `src/tabMoves.ts`, `src/tabDrag.ts`, `src/tabTransfer.ts`. Builds on `2026-11-21-split-and-tear-off-one-process.md`: every window is in one process, so a tab moves through memory.

## Context
Phase 1 let a tab be dragged inside its window: along a tab bar, into the other pane, or to the edge of the file area to split. Let go outside the window, the tab stayed. The owner asked for tabs that drag into their own window "like you can with browsers". The lead's review of the cross-process WIP (`claude/split-and-tear-off-xproc-wip`, not merged) settled the shape: the data stays in memory, Linux needs an OS drag (on Wayland the pointer stays with the window the button went down in), and Windows can keep the pointer in the page.

## Chosen
**What moves, and how.**
- The tab's record is `tabTransfer.ts`'s: folder, sort, Back and Forward history, filter text, tag filter and private flag. The display mode (Details, Grid, Miller…) is one setting for every window, not a tab's, so there's no per-tab view to carry.
- The source page hands the record to the backend when the drag leaves its window (`tab_drag_start`) or on Move to New Window (`tab_to_new_window`). The backend holds it with the source window's label and the tab's id until the drag ends. The receiving page gets it in its `tab-drop` event, or, in a new window, from `window_start` (`Start::Transfer`). It checks it field by field (`parseTransfer`): an absolute path; at most 500 history entries each way, absolute paths only; a known sort; a record without the private flag counts as private. No flags, stdin or files.
- The source keeps its tab until a move is confirmed: `tab-drag-end` with `moved` (Linux), `tab_drag_release` answering `moved` (Windows), or `tab_to_new_window` returning. Its last tab going closes the window. Since a window's only tab moves the window (`startDragging`, phase 1), that happens only when its other tabs were closed during the drag.
- **The held record is cleared on every ending**: a drop that's taken, a cancel (Escape, GTK's `USER_CANCELLED`, the pointer back in its window on Windows), a drop nothing takes (handed to the new window once), a failed new window, the source window closing or reloading mid-drag (`forget`, from `app_windows`), and a new drag replacing one whose end never came. Each is a cargo test in `tab_drag.rs` (`a_cancelled_drag_leaves_nothing_held_and_the_tab_where_it_was`, `the_source_window_closing_or_reloading_drops_the_drag`, `a_drop_nothing_takes_hands_the_tab_to_a_new_window_once`, `a_new_drag_drops_one_whose_end_never_came`).

**Where a tab lands in another window** is phase 1's rule. Over a tab bar, it's inserted at the gap. Over a pane's file area: unsplit, the outer quarter splits with the tab and the middle appends it; split, it's appended to that pane. Anywhere else in another window (its sidebar, toolbar, status bar), the drop opens a new window, as Chrome does. When a drag begins, every window is told (`tab-drag-began`) and sends its tab bars and file areas in CSS pixels (`tab_drop_zones`). The backend hit-tests them at the window's zoom (`zone_at`), answers the OS at once, and sends the window `tab-drag-over` with the zone, so the page draws phase 1's mark. The page applies the zone (`landTab`). The window that takes a tab takes the focus.

**The tab's own window** takes the drag anywhere: dragged back over it, its page hit-tests its own DOM with phase 1's rules, so a drop on its own window is a move inside it or nothing, never a new window.

**Linux (X11 and Wayland): a GTK drag.**
- At the window's edge with the button down (as `commands/drag_out.rs` does for files), the page calls `tab_drag_start`, and the backend starts a GTK drag from the GTK window. It has one target, `application/x-glasshouse-tab` (same app only), action MOVE, and the tab's name as its icon. No folder URI goes with it, so a drop on another app does nothing.
- Every window's WebKitWebView has `drag-motion`, `drag-leave` and `drag-drop` handlers, attached as the window is made. They act only when the drag offers that target and comes from this process (`gtk_drag_get_source_widget`), and they stop the signal there, so WebKit doesn't see it. Any other drag (files from another app) goes on to wry and WebKit as before; this was checked by hand.
- At the source: `drag-failed` with `NO_TARGET` (a drop on nothing) opens a new window at the pointer, and returns Stop, so the icon doesn't fly back. `USER_CANCELLED` (Escape) leaves the tab. `drag-end` tells the page how it went.
- **The release WebKit missed.** The press that started the drag went to WebKit, but its release went to GTK's drag. Without a release, WebKit counts button 1 as still down. By the rule for chorded buttons, it then fires no `pointerdown` for the window's next press, only a `pointermove`. So the next drag in that window (a tab, files, a selection) didn't start, and the one after did; plain clicks worked. Found under Xvfb. When the drag ends, `gtk_dnd::release` hands the source webview a synthetic button-1 release, at the pointer and kept inside the view. The page swallows the click it may make, from the hand-off until `tab-drag-end` or the next press (`tabMoves.ts`). The file drag-out in `commands/drag_out.rs` starts its OS drag the same way, and likely has the same problem; it's left for its own change.

- **No text selection from the drag.** WebKit lets a press on `user-select: none` content start a text selection, and extends it from pointer moves outside the view. Dragging a tab out of the window selected text in the selectable parts of the page (the inspector's preview, fields). `beginTabDrag` now blocks `selectstart` until the press ends, and drops any selection the drag made (`keepSelection` in `tabDrag.ts`). Found under Xvfb.

**Wayland: what a drop on nothing reports.**
- On X11, a drop where no window takes the tab is `NO_TARGET`. A Wayland compositor tells the source only that its drag was cancelled (`wl_data_source.cancelled`), and GTK 3's Wayland backend reports that as `GDK_DRAG_CANCEL_ERROR`, which `drag-failed` gets as `ERROR`. Escape comes from GTK's own grab in the source window, so it is `USER_CANCELLED` on both.
- Chosen (`gtk_dnd::tears_off`, with a cargo test): `NO_TARGET` opens a new window on both. On Wayland, `ERROR` does too. `USER_CANCELLED`, `GRAB_BROKEN` and `TIMEOUT_EXPIRED` leave the tab. On X11, `ERROR` is a real failure and leaves the tab.
- The cost: on Wayland, a drag the compositor ends for some other reason also opens a window. The tab moves whole, so nothing is lost, and a drop on nothing is by far the common case.
- **Not checked on a real compositor.** The nested niri (26.04, winit backend) driven by a `zwlr_virtual_pointer_v1` client couldn't complete any drag between two clients, so it can't tell these apart. A plain GTK 3 file drag to a plain GTK 3 drop target failed the same way as the tab: after `start_drag`, the compositor kept sending pointer motion to the source and cancelled the drag at the release. Events also reached clients in batches about a second apart. Hand checks with a real mouse on GNOME and KDE are in `docs/testing/linux.md` (L9.14). `drag-failed` logs its result at info level with the display type, so a report from the field shows what the compositor said.

**Windows: the page keeps the pointer.**
- The webview holds the mouse capture while the button is down, so the drag never becomes an OS drag. Out of the window (`beginTabDrag`'s "track" mode), the page calls `tab_drag_start` once. After that it calls `tab_drag_hover` only when the pointer has moved, with one call in flight and at most one more queued, and stops as soon as the pointer is back in or the button is up. No call goes out while the pointer is still.
- The backend finds the window under the cursor with `GetCursorPos`, `WindowFromPoint` and `GetAncestor(GA_ROOT)`, and matches it against the app's windows' HWNDs. The point goes into that window's CSS pixels through its inner position and scale factor (`webview_point`), then its zoom.
- On release outside, `tab_drag_release`: over another window's zone, `tab-drop` there and `moved`; anywhere else, a new window at the cursor. Back in its own window, or Escape, `tab_drag_cancel`.
- No OS drag means no drag image outside the window: the window under the pointer draws the tab's name at the pointer (`label` in `tab-drag-over`); over the desktop nothing is drawn.

**A new window at the drop** has the source window's size. It's placed so the pointer is over its first tab, using an anchor the page sends: the tab bar's left edge plus 40 CSS pixels, at its middle, times the zoom. Then it's fitted to the work area of the screen under the pointer (`window_fit::place`, Keep). Its label may be one the window-state plugin has a saved size and place for, so the plugin's restore is overridden for it: unmaximized, sized and placed. On Wayland the pointer's position isn't known, and the compositor places the window.

**Move to New Window** on the tab menu (hidden for a window's only tab) does the same without a drag. It's the keyboard and accessibility path. The window opens where the OS puts it, with the focus.

**The session** has the moved tab from the moment the new window is made: a `Transfer` window's registry entry starts with a report made from the tab (none for a private one), until its page reports. Every page reports its own tabs as before, so a tab is in exactly one window's report, and private tabs stay out.

## Known limits
- The hand-off on Linux happens at the window's edge. So a glasshouse window lying over part of the tab's own window is reached only after the pointer leaves the tab's own window.
- A tab dragged from another glasshouse process (a guest started with paths, or a dev build next to a release) is refused: its record isn't in this process.
- The `cfg(windows)` code is first built by the windows-latest CI job. `tab_drag/win32.rs` was type-checked here through a scratch crate (clippy with `-D warnings` for `x86_64-pc-windows-msvc`), along with the HWND comparison against tauri's windows 0.62 type. The Windows behavior is hand-check items in `docs/testing/windows.md`.
